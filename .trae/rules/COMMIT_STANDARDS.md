## 1. 最小化变更原则

### 核心定义

每个提交必须仅包含**单一功能或修复的完整实现**，确保变更的原子性和可回滚性。

### 实施规则

#### 1.1 单一职责提交

**✅ 正确示例**
```
提交1: feat: 添加玩家等级系统核心逻辑
提交2: feat: 实现等级提升经验计算
提交3: fix: 修复等级上限检查逻辑错误
提交4: docs: 更新等级系统API文档
```

**❌ 错误示例**
```
提交1: feat: 添加等级系统+修复bug+更新文档+优化性能
```

#### 1.2 提交粒度标准

| 变更类型 | 提交粒度 | 示例 |
|----------|----------|------|
| **新功能** | 每个独立功能一个提交 | 添加装备系统、添加技能系统 |
| **Bug修复** | 每个Bug一个提交 | 修复内存泄漏、修复并发问题 |
| **重构** | 每个重构目标一个提交 | 重构数据库访问层 |
| **文档** | 每个文档主题一个提交 | 更新API文档、添加使用指南 |
| **性能优化** | 每个优化点一个提交 | 优化缓存命中率、减少数据库查询 |

#### 1.3 回滚安全要求

每个提交必须满足：
- [ ] 独立可回滚（`git revert [commit]` 不会破坏其他功能）
- [ ] 独立可构建（回滚后项目仍能编译通过）
- [ ] 独立可测试（回滚后相关测试仍能通过）

### 提交前自检

```bash
# 1. 检查变更范围
git diff --stat

# 2. 确保只包含相关变更
git diff --name-only

# 3. 检查提交信息
git log --oneline -1

# 4. 验证可回滚性
git revert --no-commit HEAD
# 检查项目是否仍能编译运行
git revert --abort
```

## 2. 原子性修改要求

### 核心定义

每次代码修改严格限制在**单个文件范围内**，避免多文件关联变更，确保变更的独立性和可维护性。

### 实施规则

#### 2.1 单文件修改原则

**✅ 正确示例**
```
提交1: 修改 PlayerData.java - 添加等级字段
提交2: 修改 PlayerManager.java - 添加等级管理方法
提交3: 修改 LevelConfig.java - 添加等级配置
```

**❌ 错误示例**
```
提交1: 同时修改 PlayerData.java + PlayerManager.java + LevelConfig.java
```

#### 2.2 跨文件依赖处理

当功能需要修改多个文件时，按依赖顺序分步提交：

```
步骤1: 修改底层接口/抽象类
步骤2: 修改实现类（依赖步骤1）
步骤3: 修改调用方（依赖步骤1、2）
步骤4: 修改配置文件（依赖步骤1、2、3）
```

#### 2.3 文件变更优先级

| 优先级 | 文件类型 | 说明 |
|--------|----------|------|
| 1 | 接口/抽象类 | 先定义契约 |
| 2 | 实现类 | 再实现功能 |
| 3 | 配置类 | 最后配置参数 |
| 4 | 测试类 | 验证功能正确性 |
| 5 | 文档类 | 更新使用说明 |

### 原子性检查清单

- [ ] 本次提交只修改了一个文件
- [ ] 修改内容聚焦于单一功能点
- [ ] 不引入未使用的导入或代码
- [ ] 不修改与当前功能无关的代码
- [ ] 代码格式化单独提交（如有必要）

## 3. 可追溯性规范

### 核心定义

每个代码变更必须包含**清晰、详细的提交注释**，并同步更新相关技术文档，确保所有变更都有完整的记录。

### 实施规则

#### 3.1 提交信息格式

```
<type>(<scope>): <subject>

<body>

<footer>
```

**格式说明**

| 部分 | 必填 | 说明 |
|------|------|------|
| `type` | ✅ | 变更类型 |
| `scope` | ❌ | 影响范围（模块/插件名） |
| `subject` | ✅ | 简短描述（不超过50字符） |
| `body` | ❌ | 详细描述（多行） |
| `footer` | ❌ | 关联信息（Issue/PR等） |

#### 3.2 提交类型规范

| 类型 | 说明 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat: 添加玩家等级系统` |
| `fix` | Bug修复 | `fix: 修复内存泄漏问题` |
| `docs` | 文档更新 | `docs: 更新API使用说明` |
| `style` | 代码格式 | `style: 统一代码缩进` |
| `refactor` | 重构 | `refactor: 优化数据库查询` |
| `perf` | 性能优化 | `perf: 减少缓存未命中` |
| `test` | 测试相关 | `test: 添加单元测试` |
| `chore` | 构建/工具 | `chore: 更新Gradle配置` |

#### 3.3 提交信息示例

**简单修复**
```
fix(scheduler): 修复任务调度器内存泄漏

- 在任务完成时正确清理引用
- 添加定时清理机制

Closes #123
```

**功能添加**
```
feat(level): 添加玩家等级系统核心功能

- 实现等级经验计算算法
- 添加等级提升事件
- 集成到玩家数据管理器

- 经验公式: 所需经验 = 基础经验 × (1.5 ^ 等级)
- 支持配置文件中自定义参数

BREAKING CHANGE: 玩家数据表新增 level 字段

Closes #456
Related to #789
```

**文档更新**
```
docs(api): 更新 RPGCore API 使用文档

- 添加 SyncScheduler 使用示例
- 补充并发安全最佳实践
- 更新版本兼容性说明

See: docs/reference/RPGCORE_API_REFERENCE.md
```

### 文档同步要求

#### 3.4 必须同步更新的文档

| 变更类型 | 必须更新文档 | 可选更新文档 |
|----------|--------------|--------------|
| 新增API | API参考文档 | 使用示例、最佳实践 |
| 修改API | API参考文档、迁移指南 | 更新日志 |
| 修复Bug | 修复记录 | 已知问题列表 |
| 性能优化 | 性能基准测试报告 | 优化指南 |
| 配置变更 | 配置说明文档 | 部署指南 |

#### 3.5 文档更新检查清单

- [ ] 代码注释已更新（JavaDoc/KDoc）
- [ ] API文档已更新（如有变更）
- [ ] 配置文件示例已更新
- [ ] 更新日志(CHANGELOG.md)已更新
- [ ] 修复记录（如适用）已创建

```markdown

- <变更点1>

- <影响点1>
```

## 6. 实施流程

### 6.1 标准开发流程

```
1. 创建功能分支
   git checkout -b feat/level-system develop

2. 进行代码修改（单文件）
   # 修改 PlayerData.java

3. 提交变更
   git add PlayerData.java
   git commit -m "feat(level): 添加玩家等级字段到PlayerData

   - 添加 level 和 exp 字段
   - 添加 getter/setter 方法
   - 更新数据序列化逻辑

   Closes #456"

4. 继续下一个文件
   # 修改 PlayerLevelManager.java
   git add PlayerLevelManager.java
   git commit -m "feat(level): 实现等级管理器

   - 添加经验计算逻辑
   - 实现等级提升检查
   - 集成事件系统

   Related to #456"

5. 更新文档
   git add docs/reference/LEVEL_SYSTEM.md
   git commit -m "docs(level): 添加等级系统文档

   - API使用说明
   - 配置参数说明
   - 最佳实践指南

   Related to #456"

6. 推送并创建PR
   git push origin feat/level-system
```

### 6.2 紧急修复流程

```
1. 创建修复分支
   git checkout -b fix/memory-leak main

2. 修复代码（单文件）
   git add SchedulerManager.java
   git commit -m "fix(scheduler): 修复任务调度器内存泄漏

   问题描述:
   长时间运行后内存持续增长，最终导致OOM

   根因分析:
   已完成任务未从队列中移除，导致引用累积

   修复方案:
   - 在任务完成时立即移除队列引用
   - 添加定期清理机制

   验证步骤:
   1. 运行压力测试24小时
   2. 监控内存使用情况
   3. 确认无内存增长

   Fixes #789"

3. 推送并创建PR
   git push origin fix/memory-leak
```
